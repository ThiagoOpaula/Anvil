# Step 3 — Profile system + Linux launcher discovery

> **Baseline:** `e18d05a` (v0.5.0), tree clean except untracked `.mimocode/`.
> **Execution:** delegate to a `general` subagent. Model: `deepseek/deepseek-flash`
> (validated tier — **not** `deepseek-v4.1-flash`, which does not exist in the host
> registry; re-confirm with `actor models` before spawning).

## Goal

Two user-facing features in one release (→ **v0.6.0**, MINOR):

1. **Profile system** — named mods folders persisted in `config.toml`, selectable from
   the CLI (`--profile NAME`) and managed in the GUI Settings tab.
2. **Linux launcher discovery** — find mods folders across the launchers Linux users
   actually run (official, Prism native + Flatpak, MultiMC, Modrinth App, …) instead of
   assuming `~/.minecraft/mods`.

They ship together because they compound: discovery produces the candidates, profiles
store the choices.

### Non-goals

- Drag & drop JARs and every other open ROADMAP item.
- Packaging (`.deb`/`.rpm`/AUR) — that is the separate "Linux/macOS packages" item.
- Any new network behaviour. `deps.rs`, `updater.rs`, `api.rs`, `cache.rs` untouched.
- macOS-specific roots: **macOS is not in the CI matrix**, so any `cfg(target_os = "macos")`
  branch would never be compiled. Keep it trivial.
- Preserving TOML comments on GUI save (needs `toml_edit`; declined — see §2).

# Part A — Profile system

## A1. Types (`src/types.rs`)

Append to `Config` (after `dark_mode`, `types.rs:312`):

```rust
#[serde(default, skip_serializing_if = "Vec::is_empty")]
pub profiles: Vec<Profile>,
#[serde(default, skip_serializing_if = "Option::is_none")]
pub active_profile: Option<String>,
```

New type beside `Config`:

```rust
#[derive(Debug, Clone, Serialize, Deserialize, PartialEq)]
pub struct Profile {
    pub name: String,          // required — no serde(default)
    pub mods_dir: PathBuf,     // required — no serde(default)
    #[serde(default)] pub loader: Option<String>,
    #[serde(default)] pub game_version: Option<String>,
}
```

Three deliberate deviations, each worth a one-line doc comment:

- `profiles` is `Vec<Profile>`, **not** `Option<Vec<Profile>>` — absent and `[]` are
  semantically identical, so `Option` adds nothing and forces `.unwrap_or_default()` at
  every use. It breaks the file's `Option<T>` convention; say so.
- `skip_serializing_if` is used **nowhere** in the crate today. It keeps a profile-less
  `config.toml` byte-identical to current output.
- `name`/`mods_dir` carry no `#[serde(default)]`, so a typo'd `[[profiles]]` entry fails
  loudly in `config::load` (already mapped to `Error::Config`) instead of becoming an
  unreachable profile.

⚠️ **`Config` is not compiler-protected.** It derives `Default` (`types.rs:272`) and every
field is `#[serde(default)]`, so a forgotten field compiles and tests green. `ResolvedConfig`
has no `Default`, so *it* is protected. Assert the new `Config` fields in `tests/types.rs`.

## A2. `ResolvedConfig` (`src/config.rs:35-60`) — add 3 fields

```rust
pub profiles: Vec<Profile>,
pub active_profile: Option<String>,
pub config_path: PathBuf,   // so save_settings stops re-deriving the path
```

`profiles`/`active_profile` must live here, not only on `Config`: `AnvilApp` receives only a
`ResolvedConfig` (`bin/gui.rs:110`) and the Settings tab has to render the list. Otherwise the
GUI re-reads `config.toml` and there are two sources of truth.

## A3. Resolution (`src/config.rs`)

Extract the whole precedence ruleset into one function and call it from **both** binaries —
`bin/gui.rs:52-91` currently hand-duplicates it, and duplicating profile lookup there is exactly
the bug class this feature must avoid:

```rust
pub fn resolve_from_file(
    file: Config,
    cli_mods_dir: Option<PathBuf>,
    common: Option<&CommonArgs>,
    profile_flag: Option<&str>,
    config_path: &Path,
) -> Result<ResolvedConfig>
```

`config::resolve` (`:93`) becomes `load()` + `resolve_from_file(...)`. `bin/gui.rs` calls it with
`(file, None, None, None, &config_path)` — so the GUI honours `active_profile` for free.

**Precedence**

| field | order |
|---|---|
| `mods_dir` | `--mods-dir` > `--profile NAME` > `active_profile` > `file.mods_dir` > `paths::default_mods_dir()` |
| `loader` / `game_version` | CLI flag > selected profile > `file.*` > auto-detect (`None`) |

Auto-detect stays the existing `None` contract — do **not** add a fourth step to `resolve`;
`interactive::prompt_if_needed` only fills `None` values.

`mods_dir` must stay **un-canonicalized** in `resolve` — `tests/config.rs:63` asserts
`Some(PathBuf::from("/my/mods"))` verbatim, and canonicalizing mangles relative Windows paths.

**Error behaviour — deliberately asymmetric**

| situation | behaviour |
|---|---|
| `--profile X` given, X absent | **hard error**, `Error::Config` (`error.rs:26`) — reuse it, add no variant |
| `active_profile` stale/missing, `profiles` empty | `tracing::warn!` + fall through to `file.mods_dir` → default. Never error |
| duplicate profile names | first match wins, no error |

Rationale: `--profile X` is an explicit instruction and quietly operating on a *different* mods
folder is destructive (backups and writes land in the wrong tree). A stale `active_profile` is a
leftover the user did not re-assert; erroring would brick every command until they hand-edit TOML.

Backward compatibility: a config with only `mods_dir` and no `profiles` resolves exactly as today.
Cover it with an explicit regression test.

## A6. GUI — the `save_settings` data-loss bug (highest risk)

`save_settings` (`app.rs:1515-1573`) builds a **fresh** `Config` literal and overwrites
`config.toml` wholesale; it never reads the file. `app.rs:1519/1565/1567` is the only config
writer in the crate. Consequences today, all of which the fix must address:

1. Adding `profiles`/`active_profile` as unpopulated fields ⇒ **every GUI save wipes every profile.**
2. `verbose`/`quiet`/`dry_run` are forced to `None` (`:1549-1551`) ⇒ every GUI save deletes a
   hand-written `dry_run = true` from the file. Pre-existing bug, fixed for free.
3. Every IO error is discarded (`let _ =` at `:1522`, `:1567`) while the caller unconditionally
   logs `"Settings saved."` (`:1402-1404`).

Fix — read-modify-write, and make the merge testable without the `gui` feature by extracting it
into `src/config.rs`:

```rust
// src/config.rs
#[derive(Debug, Clone, Default)]
pub struct SettingsForm {
    pub mods_dir: Option<PathBuf>,   // None while a profile is active
    pub backup: bool, pub loader: Option<String>, pub game_version: Option<String>,
    pub include: Option<Vec<String>>, pub exclude: Option<Vec<String>>,
    pub max_updates: Option<usize>, pub confirm: bool, pub changelog: bool, pub dark_mode: bool,
    pub profiles: Vec<Profile>, pub active_profile: Option<String>,
}

/// Apply GUI-owned settings onto an existing Config, preserving every key the GUI
/// does not own. TOML comments and unmodelled keys are still lost (needs toml_edit).
pub fn merge_settings(existing: Config, form: &SettingsForm) -> Config
```

`save_settings(&mut self)` becomes: `load(&config_path).unwrap_or_default()` →
`merge_settings(cfg, &form)` → `toml::to_string_pretty` → write, returning `Result` so the
caller reports failure instead of always printing "Settings saved.".

Four invariants the merge encodes:

- never construct a `Config` from scratch;
- never assign `None` to a key the GUI does not own (`verbose`, `quiet`, `dry_run`, and any
  future key);
- **do not write `mods_dir` while a profile is active** — otherwise the profile's path freezes
  into the global key and survives a later switch to `(none)`;
- `profiles` and `active_profile` are GUI-owned and always written.

# Part B — Linux launcher discovery

## B1. Why a separate module

`src/paths.rs` documents itself as doing **no** filesystem IO (`paths.rs:1-4`). Discovery reads
directories and parses JSON, so it becomes a new module — which also leaves `tests/paths.rs`
untouched. Register `pub mod discover;` in `src/lib.rs` between `deps` (`:14`) and `error` (`:15`).

No `Cargo.toml` change: `serde_json` (`:21`) and `dirs` (`:30`) are already direct deps. No
`walkdir`, no `glob`, no `rfd`.

## B2. Public API (`src/discover.rs`)

```rust
//! Launcher mods-folder discovery. Never reports a path that does not exist.

#[derive(Debug, Clone, Copy, PartialEq, Eq, PartialOrd, Ord)]
pub enum LauncherKind { Official, FlatpakOfficial, Prism, MultiMc, ModrinthApp, AtLauncher, GdLauncher }
impl LauncherKind { pub fn label(self) -> &'static str }

#[derive(Debug, Clone, Copy, PartialEq, Eq)]
pub enum RootKind {
    ModsDir,      // root IS the mods folder
    GameDir,      // root/mods
    InstancesDir, // expand one level; Prism/MultiMC/ATLauncher layout
    ProfilesDir,  // expand one level; Modrinth App layout
}

#[derive(Debug, Clone, PartialEq, Eq)]
pub struct RootSpec { pub launcher: LauncherKind, pub root: PathBuf, pub kind: RootKind }

#[derive(Debug, Clone, PartialEq, Eq)]
pub struct DiscoveredModsDir {
    pub mods_dir: PathBuf,   // canonical when resolvable
    pub launcher: LauncherKind,
    pub root: PathBuf,       // raw root, for display
    pub jar_count: usize,    // direct *.jar children
}

pub fn root_specs() -> Vec<RootSpec>;            // paths only, no IO
pub fn discover_from(specs: &[RootSpec]) -> Vec<DiscoveredModsDir>;   // PURE core
pub fn discover() -> Vec<DiscoveredModsDir>;     // discover_from(&root_specs())
pub fn official_custom_game_dirs(json_paths: &[PathBuf]) -> Vec<PathBuf>;  // PURE, never Err
```

`discover_from` being pure and spec-driven is what makes the whole feature testable on **both**
CI platforms with temp dirs — only the ~15-line `root_specs()` is platform-specific.

## B3. Probe algorithm

| `RootKind` | candidates, in order | accept |
|---|---|---|
| `ModsDir` | `root` | first `is_dir()` |
| `GameDir` | `root/mods` | first `is_dir()` |
| `InstancesDir` | each direct child `e` that is a dir and whose name does not start with `.`: `e/minecraft/mods`, `e/.minecraft/mods`, `e/mods` | **first** hit only |
| `ProfilesDir` | same iteration, order `e/mods`, `e/.minecraft/mods` | **first** hit only |

Invariants that make "never report a non-existent path" true by construction:

- any `read_dir`/`metadata` error (missing root, permission denied, deleted instance) ⇒ that root
  contributes **nothing**; never panics, never returns `Err`;
- `is_dir()` is the only acceptance test, so a regular *file* named `mods` never qualifies;
- traversal depth ≤ 2 — no recursion;
- `official_custom_game_dirs` parses `serde_json::Value`, walks `["profiles"]` (object), and for
  each entry accepts **either** `"gameDir": "…"` **or** `"gameDir": {"path": "…"}`. Malformed,
  absent, or non-object ⇒ `vec![]`. Results are fed back in as `GameDir` specs.

**Dedup + ordering:** `fs::canonicalize` each candidate (fall back to the raw path on error),
dedup by canonical path keeping the first (preserving its `launcher`/`root` for display), emit the
canonical path, then sort by `(launcher, mods_dir)`. Canonicalizing collapses a symlinked
`~/.minecraft/mods` into one row and gives the GUI a stable path to persist. The sort is required
for deterministic output *and* stable tests.

## B4. Roots — with honest confidence levels

| launcher | root(s) | kind | confidence |
|---|---|---|---|
| Official / legacy / SKLauncher | `dirs::home_dir()/.minecraft` | `GameDir` | **high** |
| Official custom `gameDir` | each entry from `launcher_profiles*.json` | `GameDir` | **high** for the semantic; medium for JSON shape (both shapes tolerated) |
| Prism native | `dirs::data_dir()/PrismLauncher/instances` | `InstancesDir` | **high** — Prism docs; `~/.local/share/PrismLauncher` |
| Prism Flatpak | `~/.var/app/org.prismlauncher.PrismLauncher/data/PrismLauncher/instances` | `InstancesDir` | **high — verified on this machine** |
| MultiMC | `dirs::data_dir()/{MultiMC,multimc}/instances` | `InstancesDir` | medium; probe both casings, cheap |
| Modrinth App native | `dirs::data_dir()/ModrinthApp/profiles` | `ProfilesDir` | medium-high |
| Modrinth App Flatpak | `~/.var/app/com.modrinth.ModrinthApp/data/ModrinthApp/profiles` | `ProfilesDir` | medium |
| ATLauncher | `dirs::data_dir()/ATLauncher/instances` | `InstancesDir` | **guess** |
| GDLauncher | `dirs::config_dir()/gdlauncher_next/instances` | `InstancesDir` | **guess — lowest confidence** |
| Flatpak official launcher | `~/.var/app/com.mojang.Minecraft/.minecraft` | `GameDir` | **guess** |

Rules for reading this table:

- **Guesses are safe and therefore acceptable.** Every root is probed, and a wrong guess degrades
  to *silence*, never to a wrong path. Prefer a slightly wider candidate set over a minimal one.
- Derive paths from `dirs::data_dir()` / `dirs::config_dir()` (already XDG-aware via the `dirs`
  crate) rather than hardcoding `~/.local/share` and `~/.config`.
- The `~/.var/app` flatpak roots are the only `cfg(target_os = "linux")` block; honour
  `$FLATPAK_USER_DIR` if set, else `home_dir()/.var/app`.

### ⚠️ Unresolved: the Prism/MultiMC instance layout

Whether an instance's game dir is `<instance>/minecraft` or `<instance>/.minecraft` could **not**
be established — this machine's Prism data dir has no live instances (only `.tmp/`,
`instgroups.json`), `PrismLauncher-0.log` records instance *names* but never game directories, and
the repo has no prior art. Upstream MultiMC/Prism almost certainly uses `minecraft/` (siblings
`instance.cfg`, `mmc-pack.json`, `patches/`), but that is medium confidence and unfalsified.

The candidate order in §B3 tolerates both at the cost of one extra `is_dir()` per instance — that
is the resolution. **Do not** narrow it to one path on a hunch. `instance.cfg`'s game-dir override
is a known gap: an instance with a relocated game dir is not auto-detected and has to be added as a
profile by hand. Leave a code comment saying so.

- GUI: the Detect button in the Settings Profiles section populates `detected_dirs`; each row's
  `Add` creates a profile named from the launcher + instance, deduped (`prism-spark`, `vanilla`).
